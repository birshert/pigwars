# PigWars — RFC 005: Ежедневная утренняя сводка по группе

## 1. Кратко

Этот RFC добавляет в PigWars автоматический **утренний групповой дайджест за вчера**.

Каждое утро бот публикует в чат один пост, который коротко отвечает на вопрос:

* что произошло в игре за вчера;
* какие были главные события;
* кто сильнее всего отличился;
* в каком состоянии группа входит в новый день.

Ключевой принцип первой итерации:

* суммаризация делается **LLM по структурированным игровым фактам**, а не по сырому чату;
* сообщение отправляется **автоматически воркером**;
* если LLM недоступна, бот всё равно шлёт **детерминированный шаблонный дайджест**;
* расчёт “вчера” и время отправки в первой версии живут в **игровом часовом поясе МСК**, потому что текущая игра уже использует `Europe/Moscow`.

Пример:

* утром **19 марта 2026** бот публикует сводку за **18 марта 2026, 00:00-23:59 МСК**.

---

## 2. Что решает этот RFC

Сейчас PigWars хорошо умеет сообщать о событиях в моменте:

* результаты боёв;
* результаты рейдов;
* объявления мировых событий;
* ответы на пользовательские команды.

Но у проекта нет слоя “ретроспективы дня”.

Из-за этого теряются три важных эффекта:

* группа не получает общего ощущения “каким был вчерашний день”;
* игрок, который пропустил часть активности, не видит короткую сводку вместо чтения всей истории;
* у бота нет регулярного утреннего ритуала, который возвращает внимание в игру.

Нужен один ежедневный пост, который делает из разрозненных событий читаемую историю.

---

## 3. Цели

### Основные цели

* Дать каждой группе один короткий утренний пост с итогами вчерашнего дня.
* Повысить ежедневную возвращаемость без добавления обязательного действия для игрока.
* Собрать разрозненные игровые события в понятный нарратив.
* Сохранить мемный тон PigWars, но не жертвовать фактической точностью.
* Встроить механику в текущую архитектуру `worker` + PostgreSQL + `pig_events`.

### Не цели

* Не анализируем обычную переписку Telegram-чата.
* Не строим полноценную BI-систему или аналитический кабинет.
* Не заменяем лайв-уведомления о боях, рейдах и мировых событиях.
* Не обещаем сложные исторические инсайты вроде “вышел на 1 место относительно утра”, если в БД нет нужного snapshot-слоя.
* Не делаем в первой версии персональные дайджесты в личку.

---

## 4. Текущее состояние системы

В кодовой базе уже есть почти все базовые кирпичи для такой фичи:

* `app/worker.py` уже периодически обходит группы и отправляет системные сообщения;
* `app/infra/scheduler.py` уже даёт простой цикл для фоновых задач;
* `pig_events` уже пишет важные игровые события:
  * `pig_created`
  * `pig_fed`
  * `battle_ready`
  * `battle_won`
  * `battle_lost`
  * `raid_started`
  * `raid_finished`
  * `item_found`
  * `item_used`
  * `item_equipped`
  * `sabotage_success`
  * `sabotage_failed`
  * `mood_changed`
  * `loyalty_changed`
* есть отдельные таблицы `battles`, `pig_raids`, `world_events`, `pigs`, по которым можно строить агрегаты;
* игровое время уже нормализовано через `app/domain/rules/timezones.py` и МСК-день.

То есть проблема не в отсутствии данных как таковых.

Проблема в том, что сейчас у нас нет:

* отдельного сервиса, который собирает факты за день на уровне группы;
* idempotent-механизма “сводка за этот день уже отправлена”;
* слоя LLM-генерации поверх этих фактов;
* фолбэка на случай, если LLM не ответила.

## 5. Предлагаемая продуктовая модель

### 5.1 Когда отправлять

Первая версия:

* один пост **каждое утро в 09:00 МСК**;
* охватываем окно **предыдущего игрового дня по МСК**;
* отправляем сводку в каждую группу, где есть хотя бы одна свинья.

Почему так:

* текущая игра уже привязана к МСК-дню;
* не нужно сразу тащить настройку таймзон на группу;
* можно быстро и прозрачно запустить первую версию.

### 5.2 Что должно быть в сообщении

Утренний дайджест должен быть коротким и читаемым с экрана телефона.

Рекомендуемая структура:

1. заголовок вида `🌅 Хрюкодайджест за 18.03`;
2. короткий LLM-абзац на 2-4 предложения;
3. блок `Главное за вчера:` с 3-5 фактами;
4. блок `Текущий топ по весу:` с 3 лидерами;
5. при необходимости короткая концовка в стиле PigWars.

### 5.3 Какой тон нужен

Тон должен оставаться фирменным:

* мемный;
* деревенско-ироничный;
* без сухой канцелярщины;
* без выдумывания несуществующих событий.

Правило важнее стиля:

* сначала факт;
* потом смешная упаковка;
* никогда наоборот.

### 5.4 Пример целевого сообщения

```text
🌅 Хрюкодайджест за 18.03

Вчера в загоне было шумно: группа устроила 6 боёв, 4 вылазки и одну удачную диверсию. Самым бодрым оказался Пятачелло: он забрал две драки подряд и заметно отъелся. А вот Хряпыч вернулся из леса с позором, но хотя бы не с пустыми копытами.

Главное за вчера:
• 6 боёв, 4 рейда, 1 диверсия, 2 найденных предмета
• Пятачелло: +1.84 кг за день
• Милка притащила из рейда «Счастливый амулет»
• В группе появилась новая свинья: Беконтий
• Мировое событие всё ещё активно: «Ярмарка жирного корма»

Текущий топ по весу:
1. Пятачелло — 17.40 кг
2. Милка — 16.85 кг
3. Хряпыч — 15.90 кг
```

## 6. Из каких данных собирается сводка

### 6.1 Источники первой версии

Для первой итерации достаточно следующих источников:

| Источник | Что берём |
| --- | --- |
| `battles` | число боёв, победители, проигравшие, biggest swing |
| `pig_raids` | число рейдов, хорошие/плохие исходы, заметные находки |
| `pig_events` | кормления, предметы, диверсии, создание свиней, изменения настроения и лояльности |
| `world_events` | активное / начавшееся мировое событие |
| `pigs` | текущий топ группы по весу |

### 6.2 Что считаем “главными апдейтами”

В первую версию стоит включать только то, что можно честно получить из текущих данных:

* количество боёв за день;
* количество рейдов и долю удачных / провальных;
* количество диверсий и успешных диверсий;
* новые свиньи за день;
* найденные и использованные предметы;
* максимальный суммарный привес за день по свинье;
* наиболее заметный проигрыш или неудачная вылазка;
* текущий топ-3 по весу;
* активное мировое событие, если оно влияло на день.

### 6.3 Что сознательно не обещаем в первой версии

Без отдельного snapshot-слоя не стоит обещать:

* изменение места в лидерборде относительно начала дня;
* полноценные win streak-истории через много дней;
* точную “самую активную свинью” по сложной формуле;
* причинно-следственные выводы, которых нет в данных.

Если позже понадобится более богатый исторический анализ, это должен быть отдельный слой дневных снимков или отдельный RFC.

## 7. Архитектура суммаризации

### 7.1 Общий конвейер

Правильная модель для первой версии:

1. воркер определяет, что для группы пора строить дайджест;
2. facts-service собирает **структурированный JSON-контекст за день**;
3. rule-layer выбирает 3-7 самых важных фактов;
4. LLM получает только этот структурированный контекст;
5. бот отправляет итоговый текст в группу;
6. в БД фиксируется, что сводка за этот день уже отправлена.

### 7.2 Почему нельзя отдавать LLM сырые события как есть

Если слать в модель весь сырой поток:

* вырастут токены и стоимость;
* появится больше шума;
* модель начнёт замечать второстепенные события;
* увеличится риск галлюцинаций и ложных акцентов.

Поэтому LLM должна быть не “аналитиком сырого лога”, а “редактором готовых фактов”.

### 7.3 Контракт фактов

Сервис фактов должен отдавать в модель что-то близкое к такому контракту:

```json
{
  "digest_day": "2026-03-18",
  "group_title": "PigWars Chat",
  "counts": {
    "battles": 6,
    "raids_total": 4,
    "raids_good": 2,
    "raids_bad": 1,
    "feeds": 11,
    "sabotage_total": 1,
    "sabotage_success": 1,
    "items_found": 2,
    "new_pigs": 1
  },
  "highlights": [
    {"type": "top_gain", "pig_name": "Пятачелло", "weight_delta": "1.84"},
    {"type": "raid_loot", "pig_name": "Милка", "item_title": "Счастливый амулет"},
    {"type": "new_pig", "pig_name": "Беконтий"}
  ],
  "leaderboard": [
    {"place": 1, "pig_name": "Пятачелло", "weight_kg": "17.40"},
    {"place": 2, "pig_name": "Милка", "weight_kg": "16.85"},
    {"place": 3, "pig_name": "Хряпыч", "weight_kg": "15.90"}
  ],
  "world_event": {
    "title": "Ярмарка жирного корма",
    "active": true
  }
}
```

### 7.4 Правила для LLM

У модели должны быть жёсткие ограничения:

* не придумывать факты, которых нет во входе;
* не придумывать имена, числа и предметы;
* не перечислять больше 5 главных пунктов;
* не писать слишком длинное сообщение;
* сохранять юмор, но не уходить в абсурд, который ломает факты.

Рекомендуемая длина результата:

* `500-900` символов итогового текста;
* максимум `1` короткий абзац + `3-5` буллетов + лидерборд.

### 7.5 Фолбэк без LLM

Это обязательная часть дизайна.

Если LLM не ответила, превысила таймаут или вернула мусор, бот не должен “пропускать утро”.

Нужен deterministic fallback:

* заголовок;
* counts за день;
* 2-3 заранее выбранных highlight-факта;
* текущий топ-3.

Иначе механика будет выглядеть ненадёжной именно в тот момент, когда пользователь её ждёт.

## 8. Планировщик и идемпотентность

### 8.1 Где это должно жить

Логично встроить дайджест в текущий `worker`, а не делать отдельный процесс.

Причины:

* уже есть цикл `run_periodic_job`;
* уже есть доступ к `bot`, БД и групповому обходу;
* фича по природе близка к рейд-резолву и анонсам мировых событий.

### 8.2 Как определять “пора слать”

На каждом тике воркер:

1. вычисляет текущий момент в МСК;
2. если локальное время уже позже `09:00`;
3. берёт предыдущий игровой день;
4. ищет группы, для которых дайджест за этот день ещё не отправлен;
5. строит и шлёт сводку.

### 8.3 Почему нужен явный send-log

Без таблицы отправок будут проблемы:

* после рестарта возможны дубли;
* нельзя будет безопасно ретраить упавшие отправки;
* нельзя будет понять, что именно было отправлено вчера;
* невозможно будет отличить `failed` от `not attempted`.

Нужна явная idempotency-запись на уровень `group + digest_day`.

## 9. Изменения в модели данных

### 9.1 Новая таблица `group_daily_digests`

Предлагается новая таблица для учёта сводок:

| Поле | Тип | Назначение |
| --- | --- | --- |
| `id` | PK | технический ключ |
| `group_id` | FK -> `telegram_groups.id` | группа |
| `digest_day` | `date` | за какой день сводка |
| `status` | `string` | `pending`, `sent`, `failed`, `skipped` |
| `source_payload` | `json` nullable | структурированный контекст, который пошёл в генерацию |
| `summary_text` | `text` nullable | итоговый текст отправки |
| `llm_model` | `string` nullable | какая модель генерировала текст |
| `sent_at` | `timestamp` nullable | время успешной отправки |
| `telegram_message_id` | `bigint` nullable | id сообщения в Telegram |
| `error_text` | `text` nullable | причина ошибки при провале |
| `created_at` | `timestamp` | служебное поле |

Обязательное ограничение:

* `UNIQUE(group_id, digest_day)`

### 9.2 Почему не надо хранить это в `telegram_groups`

Сводка является не настройкой группы, а историей конкретного запуска.

Если попытаться засунуть это в `telegram_groups`, мы потеряем:

* историю;
* retry-state;
* прозрачную идемпотентность;
* возможность дебага по конкретному дню.

### 9.3 Нужны ли group-settings в первой версии

Нет.

Для MVP этого RFC достаточно:

* глобально включить фичу;
* отправлять всем группам по одной модели и в одно время.

Настройки вида:

* `daily_digest_enabled`
* `daily_digest_hour`
* `timezone`

лучше вынести в следующую итерацию, если механика реально докажет ценность.

## 10. Изменения в приложении

### 10.1 Новые компоненты

Рекомендуемый минимальный набор:

* `DailyDigestRepository`
* `DailyDigestFactsService`
* `DailyDigestSummaryService`
* `DailyDigestFormatter`

### 10.2 Что должен делать `DailyDigestFactsService`

Этот сервис отвечает не за текст, а за честные факты:

* выбрать окно вчерашнего дня;
* собрать counts по событиям;
* выбрать заметные highlights;
* получить текущий топ-3 группы;
* собрать компактный JSON-контекст.

### 10.3 Что должен делать `DailyDigestSummaryService`

Этот сервис:

* принимает facts payload;
* вызывает LLM-клиент;
* валидирует длину и базовую структуру ответа;
* при ошибке падает в шаблонный summary.

### 10.4 Что меняется в `worker`

В `run_worker_tick` нужно добавить ещё один блок:

* `collect due digests`
* `build facts`
* `generate summary`
* `send message`
* `mark sent / failed`

Важно:

* отправка дайджестов не должна ломать резолв боёв и рейдов;
* при одной неудачной группе воркер должен продолжать обрабатывать остальные.

## 11. Конфигурация

Для первой версии достаточно таких настроек:

* `DAILY_DIGEST_ENABLED`
* `DAILY_DIGEST_HOUR_MSK`
* `DAILY_DIGEST_LLM_TIMEOUT_SECONDS`
* `DAILY_DIGEST_MAX_GROUPS_PER_TICK`
* `DAILY_DIGEST_MODEL`

Принцип:

* если `DAILY_DIGEST_ENABLED=false`, код дайджеста не активируется;
* если модель не сконфигурирована, можно временно жить только на deterministic fallback.

## 12. Ограничения первой версии

### 12.1 Только игровые события

LLM суммаризует только то, что знает игра:

* бои;
* рейды;
* предметы;
* диверсии;
* создание свиней;
* мировые события;
* изменения игровых статов.

Обычный чат людей в Telegram в эту систему не входит.

### 12.2 Один общий час для всех

Первая версия живёт на:

* фиксированном времени;
* фиксированном часовом поясе;
* без UI-настроек.

### 12.3 Без тяжёлой исторической аналитики

Мы делаем “утренний редакторский дайджест”, а не “аналитический отчёт за сутки”.

Это сознательное ограничение.

## 13. Риски и как их гасить

### 13.1 Галлюцинации модели

Риск:

* LLM начнёт придумывать драму, которой не было.

Защита:

* слать только структурированные факты;
* жёсткий prompt;
* fallback на шаблон;
* хранить `source_payload` и `summary_text` для аудита.

### 13.2 Слишком длинные или скучные сообщения

Риск:

* пост начнут пропускать, если он разрастается или звучит как отчетность.

Защита:

* лимит длины;
* 3-5 highlights;
* короткий абзац вместо простыни текста.

### 13.3 Шум в тихих группах

Риск:

* в группе почти ничего не произошло, а бот всё равно шлёт длинную сводку.

Защита:

* отдельный “тихий день” шаблон;
* лаконичный формат для пустого дня;
* при необходимости в следующей версии можно добавить порог активности.

### 13.4 Падение внешнего LLM API

Риск:

* ежедневный ритуал ломается из-за внешнего интегратора.

Защита:

* timeout;
* fallback;
* статус `failed` с последующим retry;
* отсутствие hard dependency на один ответ модели.

## 14. План внедрения

### Этап 1. Данные и идемпотентность

* Добавить таблицу `group_daily_digests`.
* Добавить repository для записи и чтения статуса сводок.
* Добавить выборку фактов по окну `вчера`.

### Этап 2. Шаблонный дайджест

* Собрать deterministic formatter без LLM.
* Научить воркер публиковать его каждое утро.
* Проверить, что нет дублей и что сводка корректно переживает рестарты.

### Этап 3. LLM-слой

* Добавить summary-service с provider adapter.
* Ограничить вход структурированным payload.
* Оставить fallback обязательным.

### Этап 4. Тюнинг

* Подправить выбор главных фактов.
* Подправить тон.
* При необходимости вынести таймзоны и выключатели на группу в отдельный RFC.

Такой порядок важен:

* сначала надёжность доставки;
* потом красивая генерация текста.

---

## 15. Метрики успеха

После запуска стоит смотреть на:

* долю групп, где дайджест реально уходит каждое утро;
* долю `fallback`-сводок относительно `LLM`-сводок;
* среднюю длину сообщения;
* реакцию групп на посты;
* рост утренних команд после публикации дайджеста;
* число дублей или пропусков отправки.

Если говорить продуктово, главный вопрос простой:

* делает ли утренний пост игру живее и помогает ли он людям снова зайти в PigWars с утра.

---

## 16. Итоговое решение

Предлагается принять этот RFC в следующем виде:

* у PigWars появляется **ежедневный утренний дайджест за вчера**;
* первая версия работает **по МСК в 09:00**;
* суммаризация строится на **структурированных игровых фактах**, а не на сыром чате;
* **LLM используется как текстовый редактор фактов**, а не как источник истины;
* **fallback-дайджест обязателен**;
* для защиты от дублей вводится отдельная таблица `group_daily_digests`.

Это достаточно маленькое изменение, чтобы вписаться в текущую архитектуру, и достаточно заметное, чтобы создать новый ежедневный ритуал внутри групп.
