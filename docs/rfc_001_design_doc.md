# PigWars — Design Doc

## 1. Краткое описание

**PigWars** — Telegram-бот для групповых чатов, в котором каждый участник группы может завести **одну свинью** и развивать её:
кормить, набирать вес, выводить в боевой режим и участвовать в случайных драках с другими свиньями из той же группы.

Основная игровая петля:

1. Пользователь создает свинью.
2. Раз в час кормит её, увеличивая вес.
3. Раз в два часа переводит её в боевой режим.
4. Если в группе есть другие свиньи в боевом режиме, бот с некоторой вероятностью матчмит их в драку.
5. Победитель прибавляет в весе, проигравший теряет часть веса.
6. В группе доступен лидерборд по весу.

---

## 2. Цели MVP

### Что должно быть в первой версии

* Работа в **Telegram-группах**
* У одного пользователя в рамках одной группы — **не более одной свиньи**
* Создание свиньи с именем
* Просмотр своей свиньи
* Кормление свиньи **раз в 1 час**
* Вход в боевой режим **раз в 2 часа**
* Рандомный матчинг между свиньями в боевом режиме
* Проведение боя с учетом **веса и модификаторов**
* Изменение веса по итогам боя
* Лидерборд по весу в рамках группы
* Хранение состояния в Postgres
* Подъем инфраструктуры через Docker Compose
* Redis — опционально, но рекомендуется

### Что не входит в MVP

* Приватные чаты как основной режим игры
* Инвентарь, скиллы, предметы, классы свиней
* Сезоны, рейтинги, валюты, магазин
* Межгрупповые битвы
* Web UI / админка
* Сложная анимация боёв

---

## 3. Основные продуктовые правила

### 3.1 Область действия сущностей

* Бот работает **в группах**
* Свинья существует в контексте **конкретной группы**
* Один пользователь может иметь:

  * максимум **одну свинью в одной группе**
  * но в разных группах — разные свиньи

То есть уникальность такая:

`(telegram_group_id, telegram_user_id) -> одна свинья`

---

## 4. Игровая модель

## 4.1 Свинья

У свиньи есть:

* имя
* владелец
* группа
* текущий вес
* статус
* статистика побед/поражений
* время последнего кормления
* время последнего входа в боевой режим

### Стартовые параметры

* стартовый вес: **10.0 кг**
* статус по умолчанию: **idle**

---

## 4.2 Кормление

### Правило

* Кормить можно **раз в 1 час**

### Эффект

* Свинья получает случайную прибавку веса, например:

  * **от 0.4 до 1.2 кг**

### Почему так

Это:

* делает механику предсказуемой,
* но оставляет элемент рандома,
* не слишком быстро раздувает веса.

### Ограничения

* Кормление нельзя провести, если кулдаун еще не истек
* Кормление не должно вызываться дважды из-за двойной доставки Telegram update

---

## 4.3 Боевой режим

### Правило

* Пользователь может перевести свинью в боевой режим **раз в 2 часа**
* После входа в боевой режим свинья попадает в “боевой пул” группы

### Поведение

* Свинья находится в боевом режиме ограниченное время, например **15 минут**
* За это время она может быть сматчена с другой свиньёй
* Если бой не произошёл — статус автоматически сбрасывается обратно в `idle`

### Зачем TTL на боевой режим

Без TTL пул будет засоряться “вечными” свиньями, которых когда-то давно вывели в бой.

---

## 4.4 Матчинг

Твоя идея про “необязательно дерётся с первой попавшейся” — очень хорошая.
Я бы делал **не мгновенный детерминированный матчинг**, а **вероятностный матчинг через пул ожидания**.

### Предлагаемая логика

1. Пользователь жмет `/battle`
2. Его свинья попадает в пул боевого режима группы
3. Фоновый воркер раз в N секунд (например, раз в 30–60 секунд):

   * берет всех свиней группы в статусе `battle_ready`
   * перемешивает их случайно
   * пытается формировать пары
   * для каждой потенциальной пары кидает вероятность боя

### Вероятность боя

Например:

`P(fight) = 0.35 + bonus_by_wait_time`

Где:

* базовая вероятность: **35%**
* +10% за каждые 2 минуты ожидания
* максимум: **85%**

Так:

* бой не гарантирован сразу
* пары не всегда “первый со вторым”
* если свинья ждёт долго, вероятность постепенно растёт

### Ограничения матчингa

* только внутри одной группы
* свинья не может драться сама с собой
* свинья не должна одновременно участвовать в двух боях
* при матчинге нужен lock / транзакционная защита

---

## 4.5 Бой

Для MVP я бы не делал суперсложный движок. Лучше сделать:

* понятный
* веселый
* не полностью детерминированный
* с влиянием веса, но без 100% dominance тяжёлых свиней

### Предлагаемая модель боя

У каждой свиньи есть:

* **power**
* **hp**
* **dodge / agility modifier**

Эти параметры вычисляются из веса.

---

## 4.6 Влияние веса на бой

Чтобы “самая жирная” свинья не была просто всегда непобедимой, лучше сделать баланс такой:

* **тяжёлые** свиньи:

  * сильнее бьют
  * имеют больше hp
  * но медленнее и хуже уклоняются

* **лёгкие** свиньи:

  * слабее бьют
  * имеют меньше hp
  * но чаще уворачиваются / получают бонус к криту

### Простая tier-based модель

#### До 15 кг — “Поросёнок”

* +15% dodge
* -10% damage

#### 15–30 кг — “Крепыш”

* без сильных модификаторов, базовый баланс

#### 30–60 кг — “Кабан”

* +10% damage
* +10% hp
* -5% dodge

#### 60+ кг — “Танк”

* +20% damage
* +20% hp
* -15% dodge

Это легко объяснить игрокам и легко балансировать.

---

## 4.7 Формат боя

Для Telegram лучше делать бой как **текстовый и быстрый event**, а не длинный пошаговый симулятор.

### Вариант для MVP

1. Рассчитать боевой рейтинг обеих свиней
2. Добавить случайную компоненту
3. Определить победителя
4. Отправить красивое текстовое сообщение

Например:

* базовая сила = функция веса
* модификаторы = tier bonus
* случайный roll = `randint(1, 20)`

### Условная формула

```text
combat_score = base_power(weight) + tier_modifier + random_roll
```

Можно сделать так:

```text
base_power = sqrt(weight) * 10
```

Плюс:

* модификатор за tier
* небольшой рандом

### Почему не чисто от веса

Чтобы сохранить фан и апсеты — иногда маленькая свинья должна выигрывать.

---

## 4.8 Изменение веса после боя

### Базовая идея

* проигравшая свинья теряет часть веса
* победившая получает часть этого веса

### Предлагаемая механика

Проигравшая теряет:

`loss = min(max(3% от текущего веса, 0.3 кг), 2.0 кг)`

Победившая получает:

* **80% от потерянного веса**
* 20% “сгорает” как боевой расход

### Зачем с потерями

Если переносить 100%, жирные будут разгоняться слишком быстро.
Небольшое “сгорание массы” делает систему стабильнее.

### Ограничение снизу

* вес свиньи не может стать меньше, например, **3 кг**

---

## 4.9 Лидерборд

### Основной лидерборд MVP

* топ свиней группы по весу

### Формат

Показывать:

* место
* имя свиньи
* хозяина
* вес
* победы/поражения (опционально)

Пример:

```text
🐷 Топ жирнейших свиней группы

1. Беконатор — 41.2 кг (@alexey)
2. Свинтус Prime — 33.8 кг (@ivan)
3. Пятачок Смерти — 28.4 кг (@egor)
```

### Дополнительно, но необязательно в MVP

* топ по победам
* топ по винрейту
* “самая голодная свинья”
* “самая боевая”

# 5. UX и Telegram-команды

## Основные команды

### `/start`

* краткое описание бота
* если вызвано в группе — инструкция по командам

### `/help`

* список команд
* базовые правила

### `/create_pig <name>`

Создает свинью в группе.

Пример:

```text
/create_pig Беконатор
```

Правила:

* имя длиной 3–40 символов
* только одна свинья на пользователя в группе
* имя можно сделать уникальным в рамках группы или не делать уникальным — я бы **не делал обязательную уникальность**, чтобы не усложнять

---

### `/pig`

Показать свою свинью:

* имя
* вес
* статус
* победы/поражения
* время до следующего кормления
* время до следующего боя

---

### `/feed`

Покормить свинью:

* если кулдаун истек — увеличить вес
* если нет — показать оставшееся время

---

### `/battle`

Перевести свинью в боевой режим:

* если кулдаун прошел — свинья попадает в battle pool
* если нет — показать оставшееся время
* если уже в боевом режиме — сообщить об этом

---

### `/leaderboard`

Показать топ по весу в этой группе

---

### `/rules`

Краткие игровые правила

---

## Inline-кнопки

Для удобства можно добавить кнопки:

* Моя свинья
* Покормить
* В бой
* Лидерборд

Но я бы для MVP делал сначала **команды**, а кнопки — вторым шагом.

# 6. Архитектура

## 6.1 Технологический стек

### Основной стек

* **Python 3.12+**
* **uv** — управление пакетами и запуск
* **aiogram 3** — Telegram framework
* **PostgreSQL 16** — основная БД
* **Redis 7** — кеш, locks, координация фоновых задач
* **SQLAlchemy 2.0 (async)** — ORM / DB layer
* **asyncpg** — PostgreSQL driver
* **Alembic** — миграции
* **Pydantic Settings** — конфиг
* **Docker Compose** — локальный / dev запуск

### Почему aiogram

* асинхронный
* хорошо подходит под Telegram
* нормальный router / middleware stack
* удобно строить бота без лишнего шума

---

## 6.2 Компоненты системы

### 1. Bot app

Обрабатывает:

* Telegram updates
* команды
* отправку сообщений
* вызовы domain-сервисов

### 2. Worker

Фоновый процесс для:

* матчинга свиней в боевом режиме
* сброса battle mode по TTL
* возможных periodic jobs

### 3. PostgreSQL

Source of truth:

* свиньи
* группы
* статистика
* бои
* event history

### 4. Redis

Используется для:

* distributed locks
* идемпотентной обработки некоторых операций
* возможно, кэша лидербордов

> Теоретически MVP можно поднять и **без Redis**, но я бы всё же его заложил сразу — он полезен для боёв и защиты от гонок.

---

## 6.3 Выбор модели запуска Telegram

Для MVP:

* **long polling**

Почему:

* проще
* не нужен внешний HTTPS endpoint
* удобно под Docker Compose

Позже можно перейти на webhook, если бот будет реально нагружен.

# 9. Основные сценарии

## 9.1 Создание свиньи

1. Пользователь в группе вызывает `/create_pig Беконатор`
2. Бот проверяет:

   * команда пришла из группы
   * у пользователя в этой группе еще нет свиньи
3. Создает записи group/user при необходимости
4. Создает свинью с весом 10 кг
5. Возвращает сообщение об успехе

---

## 9.2 Кормление

1. Пользователь вызывает `/feed`
2. Бот находит его свинью в этой группе
3. Проверяет cooldown
4. Если можно кормить:

   * лочит запись свиньи
   * считает прибавку веса
   * обновляет `weight_kg`, `last_feed_at`
   * пишет event
5. Возвращает сообщение:

   * сколько прибавилось
   * текущий вес
   * когда можно снова кормить

---

## 9.3 Вход в боевой режим

1. Пользователь вызывает `/battle`
2. Бот находит свинью
3. Проверяет cooldown 2 часа
4. Проверяет, что свинья не в `in_battle`
5. Переводит в `battle_ready`
6. Ставит `battle_ready_until = now + 15 min`
7. Обновляет `last_battle_at`
8. Возвращает сообщение, что свинья вышла на арену

---

## 9.4 Матчинг и бой

1. Worker выбирает группу
2. Находит eligible pigs:

   * `status = battle_ready`
   * `battle_ready_until > now`
3. Перемешивает
4. Формирует пары и кидает вероятность боя
5. Для пары:

   * берет lock
   * переводит обеих свиней в `in_battle`
   * рассчитывает бой
   * обновляет веса и статистику
   * сохраняет battle record
   * переводит обеих обратно в `idle`
6. Отправляет сообщение в группу с результатом

---

# 10. Алгоритм боя — рекомендованный MVP-вариант

## 10.1 Расчет параметров

Для каждой свиньи:

```text
base_power = sqrt(weight_kg) * 10
```

Плюс tier modifier:

* Поросёнок: `+2 dodge`
* Крепыш: `+0`
* Кабан: `+3 power`
* Танк: `+5 power`, `-2 agility`

Плюс рандом:

```text
random_roll = randint(1, 20)
```

Итог:

```text
combat_score = base_power + tier_bonus + random_roll + small_special_bonus
```

### Special bonus

Можно дать маленький бонус апсета:

* если свинья легче соперника на 20%+, то +2 к шансу “ловкости”

Это сделает бои менее предсказуемыми.

---

## 10.2 Определение победителя

* кто набрал больший `combat_score` — тот победил
* при равенстве:

  * либо ничья,
  * либо победа у того, у кого выше random_roll

Для MVP я бы **избежал ничьих** и просто определял победителя по secondary roll.

---

## 10.3 Перераспределение веса

```text
loser_loss = clamp(loser_weight * 0.05, min=0.3, max=2.0)
winner_gain = loser_loss * 0.8
```

Пример:

* проигравший 20 кг
* теряет 1 кг
* победитель получает 0.8 кг

```text
Следующее кормление будет доступно через 1 час.
```

## Пример входа в бой

```text
⚔️ Беконатор вышел на арену и подозрительно хрюкает.
Он будет искать драку ближайшие 15 минут.
```

## Пример боя

```text
🐷💥 Бой на арене!

Беконатор (24.1 кг) vs Свинтус Prime (20.6 кг)

После короткой, но унизительной свиной схватки
победил: Беконатор 🏆

Беконатор получает +0.8 кг
Свинтус Prime теряет -1.0 кг
```

# 12. Redis: нужен или нет?

## Можно без Redis

Если:

* один инстанс бота
* один worker
* маленькая нагрузка
* всё через Postgres locks / transactions

## Но я бы рекомендовал Redis сразу

Для:

* distributed locks на бой и матчинг
* идемпотентности некоторых команд
* кэширования лидербордов
* будущего масштабирования

### Вывод

**Для MVP Redis не обязателен, но практически полезен.**
Я бы включил его в compose сразу.

# 13. Защита от гонок и дублей

Telegram иногда может доставлять апдейты повторно, плюс пользователь может нажать команду несколько раз.

Нужно предусмотреть:

### Для `/feed`

* row-level lock на pig
* проверка cooldown внутри транзакции

### Для `/battle`

* lock на pig
* повторная проверка статуса и cooldown

### Для worker

* lock на пару свиней / конкретные pig_id
* транзакционный переход `battle_ready -> in_battle`

### Идемпотентность

Можно хранить обработанные update_id кратковременно в Redis.

# 14. Docker Compose

## Сервисы

* `db` — PostgreSQL
* `redis` — Redis
* `bot` — Telegram bot process
* `worker` — background matchmaking process

### Почему отдельный worker

Это чище:

* бот отвечает за updates
* worker отвечает за периодические задачи
* проще масштабировать и дебажить

---

## Пример состава `docker-compose.yml`

```yaml
services:
  db:
    image: postgres:16
    environment:
      POSTGRES_DB: pigwars
      POSTGRES_USER: pigwars
      POSTGRES_PASSWORD: pigwars
    ports:
      - "5432:5432"
    volumes:
      - pg_data:/var/lib/postgresql/data

  redis:
    image: redis:7
    ports:
      - "6379:6379"

  bot:
    build: .
    command: uv run python -m app.main
    depends_on:
      - db
      - redis
    env_file:
      - .env

  worker:
    build: .
    command: uv run python -m app.worker
    depends_on:
      - db
      - redis
    env_file:
      - .env

volumes:
  pg_data:
```

# 16. Почему именно такая архитектура

## Плюсы

* простая
* хорошо ложится на MVP
* не перегружена микросервисами
* достаточно надежна
* легко дорастает:

  * до webhook
  * до нескольких bot/worker процессов
  * до richer mechanics

## Минусы

* часть логики матчинга и боёв всё равно потребует аккуратной синхронизации
* много stateful правил — надо хорошо покрывать тестами
* баланс боёв придется крутить руками по реальному фидбеку

# 19. Предлагаемые решения по спорным местам

## 19.1 Одна свинья на пользователя — где?

Явно **внутри группы**, а не глобально.

## 19.2 Имя свиньи уникально?

Нет, **необязательно**. Иначе лишняя боль.

## 19.3 Можно ли кормить в боевом режиме?

Для MVP я бы **разрешил**, если не идет сам бой.
Но если хочется проще — можно запретить кормление при `battle_ready`.

Я бы выбрал:

* `battle_ready` → кормить **нельзя**

Так меньше спорных состояний.

## 19.4 Можно ли вызвать `/battle`, если уже в пуле?

Нет. Просто отвечаем:

* “свинья уже ищет драку”

## 19.5 Что если в пуле 3–5 свиней?

Worker случайно перемешивает и подбирает пары.
Оставшаяся без пары свинья ждёт следующий тик.
